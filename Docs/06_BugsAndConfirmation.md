# 术士之战缺陷修正和行为确认

## 处理原则

以原地图实际规则为基准，明确的错误在 UE 开发版修正。原地图文件保持原样。修正不能顺手提高伤害、缩短冷却或改购物价格；这些是平衡改动，只有用户明确要求才做。

每条缺陷需要原行为、证据、触发条件、修正后行为和验证结果。静态分析能证明分支写法，却未必能证明该分支在原游戏里可达；因此区分“字段冲突”“静态缺陷”“运行确认”。本表的修正规则是后续实现要求，不表示现在已经修改或运行了游戏。

## 静态问题和修正策略

| 编号 | 原版问题与依据 | 修正规则 | 验收 |
|---|---|---|---|
| BUG01 | 待确认意图：PN/sN/SN 将攻击者 KV 也从自身输出扣除，守护指环描述仅减少受到的直接伤害 | 先保留原行为并复现；若确认非设计代价，则普通直击只扣目标平减，并审查陨石重复扣减路径。否则只改说明，不能增益装备 | 分别记录带/不带0.5护符时的输出与受伤，确认后固定期望 |
| BUG02 | 待确认意图：急行在 GN 吸收伤害，普通击退已先按未吸收量加入 | 先保留原版分离规则；若确认是顺序缺陷，再把吸收提前到普通击退计算，保持吸收池与速度奖励 | 记录同伤害在急行前后的HP与冲量，不能把降低HP伤害自动等同降低击退 |
| BUG03 | tc 等方向归一化直接除零；ID 目标预判可能除近零或对负数开方 | 统一安全归一化和有界求根，缺目标不读取无效对象；保持合法输入的原公式 | 原地瞄准、重叠目标、无目标、极低速度均无 NaN 或崩溃 |
| BUG04 | BN 的死亡竞赛分支助攻支付使用 so，不用 So | 该模式助攻用 So；击杀用 so；同人获得两种奖励时也按各自配置合计 | 自定义 so=3、So=7，击杀者与贡献者获得不同正确金额 |
| BUG05 | qb 同批次死亡逐人调用 BN，可能在批处理完成前触发终局；排序索引也依赖复用的 id | 先收集该批次死亡，按稳定顺序结算，再仅判一次回合胜负；同批全灭为平局 | 两名最后存活者同一次岩浆 tick 死亡，不先给一人胜利 |
| BUG06 | 原版临时效果大量依赖“乘倍率、到时除回来”，提前死亡或重复驱散易丢失恢复路径 | 使用有唯一 ID 的效果实例，结束幂等；重建最终属性而非反复乘除 | 靴子激活后出售、禁锢时死亡、点阵后回合切换，属性无残留 |

BUG01、BUG02 可能是原版有意的代价或伤害与击退分离机制，在意图未确认前不纳入默认修复。BUG03 的数学安全和 BUG04 的配置变量误用有明确修正方向，BUG05/06 作为新实现的安全结算要求。保留原版兼容对照测试与已确认修正版测试两套期望。若后续运行证据说明某分支不可达，将状态改为防御性修复，不伪称原版已观察到故障。

用户后续明确：不准备 Warcraft III 环境，优先直接检查地图；手感由代理决定。下表的原版运行方法保留为有条件时的验证方案，不构成开工前置。静态能确认的继续核对；静态无法唯一确定的手感或非关键交互，代理给出明确开发行为并记录其与“原版确认”状态的区别。对伤害、冷却和经济中的缺省字段继续查证，不拿手感授权替代数值证据。

## 确认记录格式

每次运行确认保存：地图哈希、地图设置、角色、技能等级与模式、装备和精通、初始 HP/K/位置、输入、实际结果、录像或截图位置、结论及影响文档。一次只改变一个变量，至少重复确认异常或随机结果。

记录路径为 `Analysis/Verification/<CaseId>/`，有证据时才创建。未能运行原地图时保持 CHECK 状态，禁止伪造截图、结果、帧率或测量。下一位开发者应先查本表，再查 JSON 与脚本，仍不能确定时运行原地图核对，而不是猜测补齐。
