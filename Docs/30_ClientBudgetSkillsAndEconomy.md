# 4K 客户端预算、技能族与经济复查

版本：v0.12 开发预览，完成本章所列构建与功能回归，120FPS性能目标尚未完全达标。交付入口为GitHub Releases，客户端与服务器均须匹配协议0x574C1002。用户验收目标为 RTX 4060、3840×2160 输出、四人战斗、高画质、120 FPS。原生 4K 与重建输出必须分开记录，不将平均超过 120 误报为全程稳定 120。

## 渲染证据与实现

最初测得游戏线程约 3ms、GPU 约 24ms，但当时另一款游戏同时占用 GPU，不能作为受控性能提升倍数的基线。原生4K专门采样仍为 GPU 瓶颈。当前场景网格密度不需要 Nanite；改用常规栅格与两级方向光阴影，保留材质、主光影与独立的 Lumen 档位；岩浆平面不投影、不参与距离场遮蔽。各预设默认高质量 TAA，仍可手选 TSR。岩浆补光原先已不投阴影，不把这一点算成新增收益。

第一次 4K 四人固定 100% 测试 GPU 均值约 12.6ms；固定 60% TAA 重建的 3240 帧样本 GPU 均值 6.46ms、总帧时间均值 7.15ms、P95 8.87ms，尚不能判为稳定 120。启动和截图预热应剔除至少 360 帧。CSV 会追加列，按最终表头解析较早短行，不能只保留与末尾表头等长的行。上述为开发过程对照，不是最终程序验收。

高画质预设启用项目自己的 TAAU 场景比例预算，读取 RHI GPU 时间与扣除帧率限制造成空等后的活跃帧时间，目标为保存的帧率上限（最高120）的80%预算，每0.25秒限速调整，范围50～100%；HUD 保持输出分辨率。ESC 明示实际比例与开关；手动调场景比例会关闭自动预算；精细预设保持固定比例。未使用引擎自动动态分辨率状态作为达标依据。

采样曾误把旧设置的60FPS预算与命令行不限帧混用：`t.MaxFPS 0`只取消限帧，不会改保存的预算目标。已修复基准脚本，临时把预算设120并逐字恢复原配置；不把该测试夹具错误解释为UE Preview的动态分辨率故障。

DS 采样另发现专服未加载角色网格但头饰仍附着头部骨骼，每 75 秒约 2.4 万条无网格 socket 警告。专服头饰改为无骨骼挂点；客户端挂点保留。新 Linux 构建运行3分42秒检查该类警告0条，空大厅约6.2%单核CPU、277MiB RSS；不是容量或长期泄漏验收。

Windows玩家包采样（RTX4060、3840×2160、高画质、4席、无其他游戏；不限帧测预算，非锁帧测试）：常规6840个战斗帧平均7.017ms（约143FPS），P95 8.330ms，P99 9.602ms，95.03%帧不超过8.333ms；GPU平均6.230ms。实际场景比例50～70.92%、平均59.16%；3422帧为四人均存活，其余三人存活。

多技能夹具用500初始金币经合法购买RPC，为四席配置不同多技能路线/升级并持续施法，不改变正式20金币默认值。9328个战斗帧平均7.518ms（约133FPS），P95 10.443ms、P99 12.958ms，80.05%帧不超过8.333ms；GPU平均5.905ms、RHI线程P95 8.410ms、游戏线程平均2.471ms，瓶颈包含渲染提交长帧。场景比例50～61%、均值52.60%；2623帧四人均存活，其余三人。该夹具仍开启0.5秒一次文件观察，不能把它当无工具开销的认证。没有把平均值称为稳定120；多技能120长帧目标仍未达标，需要进一步批处理粒子/绘制提交优化。

证据在 `Saved/Validation/client-perf-final-4k-four-high/summary.json` 与 `client-perf-final-4k-four-multiskill/summary.json`，含完整CSV和截图。首次360帧预热及非战斗阶段剔除；常规采样没有文件观察器。脚本对玩家原有配置逐字恢复。

## 技能族

`Scripts/build_skill_catalog.py` 校验原地图 SHA256，从提取 JSON 生成 `WarlockCatalogData.h`。21 个可购买技能族与 G/F 两项初始技能使用稳定 family ID；既有商品 0～20 保持兼容，新商品为 100+family。一个槽只能购买一族，等级/石头/模式仍按原图。冷却直接使用物体 acdn；双模式只开放 BF 可追踪的 R/T/E/Y 分支，不把 C 的未使用物体层误当作模式。

新增行为包括回旋镖、追踪球、疾速移动、移形换位、汲取、弹跳球、疾风步、分裂弹、爆炎、回溯、镜像、禁锢、引力、操纵及现有族的第二模式。实现尚在联动验证，不能仅以目录或 240 项基础回归称为完整原版等价。原地图 CHECK06～09 继续保留：滚石、镜像触发、逐槽沉默、回溯边界须专项对照；投射物曲线和 UE 表现属于手感实现决策。

临时效果按来源/技能独立实例到期，最终速度、输出与击退系数重建，避免乘除恢复残留。购买由服务器检查，新增 family/status 复制，项目协议从 0x574C1001 升至 0x574C1002；新旧包不混连。

最终编辑器构建的全量回归638项通过：流程89、准备/路由24、引导/商店输入29、商店构筑179、技能族276、金币15、庆祝事件10、AI战术16。Windows玩家包与Linux专服实际构建成功。离线PIE检查不等于物理手柄或原Warcraft III运行确认。

现有强化学习模型继续负责八槽选择，普通AI使用六组不同技能路线购买，专门训练课程保留；没有宣称模型已对全部新技能重新训练或沿用旧胜率校准。复杂追踪球收回交互、镜像/沉默/回溯边界及投射物曲线仍属于待对照的预览范围。

## 金币复查

本次回查直接读原图 globals、BN、VN、EN、dg、设置菜单与金币写入点，而不是依据旧文档推断。普通回合默认 yo=20、Wo=10，so/So/To/uo 均为 0；房主可改击杀、助攻、胜利、最高伤害奖金。BN 普通路径分别支付 so/So，VN 支付 To/uo，EN 在下一次准备支付 Wo。

此版本普通路径未发现“按出局名次支付金币”。KE 累积存活时间用于统计，不是金币公式。用户记忆可能涉及另一配置或版本，当前不据此捏造名次奖金。出局名次可显示，同固定步死亡应同名次，但不自动改变金币。发现新证据再修正规则。

UE 原实现只含固定补给与积分，缺少可配置金币奖励及结算明细。新增 `UWarlockEconomy` 对应六项原图配置，默认保持原值；服务器同步配置与每轮收入账目。击杀者与最大贡献助攻者分别发钱，即使为同一人也相加；胜利与并列最高伤害奖金分开。伤害/控制贡献、岩浆归属及同批死亡应继续专项验证。死亡竞赛中错误使用 so 支付助攻属于 BUG04，不把错误带入 UE 普通回合奖励。

## 击杀与胜利表现

服务器确认死亡/助攻/胜利后生成可复制的奖励事件。头顶上升飘字显示首杀、双杀、三杀、连斩、助攻或回合胜利，并显示实际积分与大于0的金币；0金币时不虚报收益。同一角色0.25秒内的击杀提示合并，避免范围多杀堆叠。增加短暂金色光环、向上火星和本地本人提示音，胜利采用更大的标题和环绕光点。效果不碰撞、不改变伤害、不冻结或震动镜头；专服不生成渲染组件、声音或逐帧表现。

10项庆祝检查覆盖实际归属/积分/零奖金、重复致死幂等、连杀、获胜事件与新局清理。PIE已检查首杀、三杀和胜利截图，修正飘字与姓名重叠，结算阶段只保留胜利标题，避免多杀提示/头顶胜利字与结算信息叠在一起；合成音频未经过人工听感验收，手感仍以试玩反馈为准。

## 联机身份回归修复

四席专服的两个客户端联测发现旧代码按当前数组下标反复改AI的PlayerId；引擎 `APlayerState` 将此属性以 `COND_InitialOnly` 同步，先后进入的客户端因此看到不同机器人编号。改为创建机器人时分配单调递减的唯一负ID，之后不因加入、人数调整或显示名称变化而重编号。已有联测的“两个客户端完整身份集合一致”断言保留，不缩减成只检查真人。

最终Windows玩家包＋远端Linux专服84项流程通过（`network-20261127-161319/report.json`），含实际渲染、独立身份/名字、房主权限、8席/6AI、Swap/Split购买及family复制、实体柱换位与开战复位、准备无伤击退、技能预览/松开/取消、HP/K一致、胜利事件/实际零金币、名次与下一轮等额补给、房主转移/重新连接。已检查该次最终胜利截图，没有多杀/头顶胜利字与主标题叠字。测试失败时旧连接会占位到30秒超时，测试清理改为先主动离开再结束进程；没有修改服务器的真实超时/满员规则。

独立打包进程的跨启动设置62项通过，含旧配置迁移、帧率/VSync、TAA/TSR、音乐/技能音量、施法触发、4/8席保存、自动预算启停/固定100%恢复、22项改键。证据 `Saved/Validation/packaged-settings.json`；测试后原玩家配置逐字恢复。

最终二进制原生4K对照：固定实际100%，四席3240战斗帧平均11.784ms（约85FPS）、P95 14.468ms、GPU平均11.194ms；只有1.08%帧≤8.333ms。证据 `Saved/Validation/client-perf-publish-native-4k-four/summary.json`。因此明确不宣称RTX4060原生4K高画质120达标。

最终二进制自动预算复测：4440战斗帧平均7.012ms（约143FPS）、P95 8.083ms、P99 9.106ms，96.78%帧≤8.333ms，GPU平均6.335ms。实际比例56.18～71.18%、均值63.24%；3421帧四人均存活，其余三人。证据 `Saved/Validation/client-perf-publish-auto-4k-four/summary.json`。这改善了常规负载，但不覆盖前述多技能负载的120长帧问题。
