## 开发开始前

1. 阅读工作区根目录和本游戏的 AGENTS.md，再读 Docs/README.md。
2. 校验原地图 SHA-256，防止换地图后沿用旧数值。
3. 检查目标技能在缺陷/确认清单中的状态，优先静态核对；Warcraft III 不作为开工前置。手感由代理决定，静态无法确认的部分记录为开发决策并在UE验证，不阻塞其余工作。
4. 确认完整 UE 和 C++ 编译环境可用；创建 `WarlockArena.uproject` 并记录引擎关联。
5. 建立项目版本控制和忽略文件。Content、Config、Source、Docs 和维护脚本纳入版本，生成缓存与打包产物忽略；二进制资产按实际工具配置 LFS。
6. 将本次已确认规则迁移为带来源的项目数据，启动时校验。禁止把整个混淆 JASS 当成 UE 运行脚本执行。

## 构建命令模板

下面只是后续项目存在后的命令模板，当前没有执行、没有编译通过记录。实际引擎路径在确认安装后填写。

```powershell
$warlockEngineRoot = 'D:\Epic Games\UE_5.9'
$warlockProject = 'D:\UE\WarlockArena\WarlockArena.uproject'

Test-Path -LiteralPath "$warlockEngineRoot\Engine\Build\Build.version"
Test-Path -LiteralPath $warlockProject

# Editor 目标编译；项目名/目标必须与实际 Target.cs 一致。
& "$warlockEngineRoot\Engine\Build\BatchFiles\Build.bat" `
  WarlockArenaEditor Win64 Development $warlockProject -WaitMutex

# 编辑器打开项目。
& "$warlockEngineRoot\Engine\Binaries\Win64\UnrealEditor.exe" $warlockProject

# Windows 开发包；必须先设好默认地图和需要烘焙的地图。
& "$warlockEngineRoot\Engine\Build\BatchFiles\RunUAT.bat" BuildCookRun `
  "-project=$warlockProject" -noP4 -platform=Win64 `
  -clientconfig=Development -build -cook -stage -pak -archive `
  '-archivedirectory=D:\UE\WarlockArena\Saved\Builds\Windows'
```

在自动化脚本中，每个入口检查文件是否存在和退出码，编译失败立即报告实际错误，不继续声称已打包。引擎版本变化时以该安装的实际构建入口和帮助参数为准，必要时更新模板。

当前 Python 分析命令为：

```powershell
python -X utf8 'D:\UE\WarlockArena\Scripts\inspect_map.py'
python -X utf8 'D:\UE\WarlockArena\Scripts\decode_objects.py'
python -X utf8 'D:\UE\WarlockArena\Scripts\build_reference.py'
```

前两项重建提取文件；第三项只重建生成章节 02、03 和机器参考表，不重写人工章节。本地 vendor 的 dclimplode 已为 Python 3.14 构建，换解释器时需重建相应原生扩展，不能盲目复制 pyd。

## 开发阶段

| 阶段 | 工作 | 必须通过的出口 |
|---|---|---|
| M0 规则核对与环境 | 静态核对关键疑点、完整引擎安装、项目和数据格式 | 原图哈希固定；不确定项与手感决策有记录；空项目可打开、编译和打包 |
| M1 运动与本地输入 | 点击与摇杆移动、双手柄路由、双LocalPlayer/分屏、0.03步、HP/K、岩浆 | 30/60/120渲染FPS下逻辑轨迹一致；两手柄不串线；岩浆按0.1秒扣血 |
| M2 核心战斗 | 火球、普通 F、命中、冲量、死亡、基本柱子 | 单次击退和高 K 轨迹与原版证据对照；公式与边界测试通过 |
| M3 联机与机器人基础 | 房主/客户端、状态复制；机器人感知与合法移动施法；本地分屏独立镜头和HUD | 两实例由服务器裁决；本地双人加AI可战斗；AI不生成视口或绕过规则 |
| M4 回合经济闭环 | 独立商店、AI构筑、技能学习升级、FFA与双人同队、下一轮和加赛 | 双人同时购物不串线；机器人合法花钱；对战及合作均可完成整场比赛 |
| M5 首版技能和构筑 | 首版六槽技能、对应模式、精通与第一页物品 | 全部开放商品有效；同槽互斥、售出、石头等路径通过 |
| M6 首版交付 | 手柄瞄准手感、断连/重连、分屏性能、AI标准难度、网络检查、Windows包 | 单人对AI、双人分屏、双人同队对AI及2～4席网络均完成全流程；真实双手柄打包版验证 |
| M7 完整规则扩展 | 其余技能、第二页装备、四角色F、更多AI策略与队伍配置 | 每个新增族完成原版确认与交互矩阵，不靠文档存在视为完成 |
| M8 可选产品扩展 | 特殊模式、外观账户、在线服务、美术替换 | 先补独立需求和验收，再实现 |

阶段可以小步穿插，但不能以单机样机代替联机首版，也不能以编译成功代替玩法验证。具体日程等开始开发并了解工具链后再估，不在此虚构工期。

AI、本地双人分屏和双手柄是新增的首版必需项，不能推迟到M7才做。优先早测设备路由、独立UI和两视口渲染，避免后期对单玩家假设大规模返工。详细输入、机器人公平性与验收见 [章节09](09_AIAndLocalMultiplayer.md)。

## 交互测试矩阵

每个开放技能至少检查敌人、友军、自身、静态柱、可动柱、敌方飞弹、同方飞弹、反射盾、岩浆、范围边缘和同点施法。无此交互的技能写明预期不响应，而不是省略检查。

每个临时效果至少检查自然结束、重复施加、被驱散、死亡、来源死亡、出售来源物品、回合清理、玩家断线。每个商品至少检查余额刚好、少1金、达到上限、前置不足、背包满、互斥和请求重复。

渲染帧率用 30/60/120 进行固定输入对比。网络验证至少包括本机双实例、约100毫秒往返延迟和少量丢包情形；记录实际使用的网络仿真设置和观察结果，不将这些设定当作已测性能承诺。

## 编译与试玩完成标准

- Editor 开发目标编译通过；重要反射和对象布局变更在关闭编辑器后完整重编译，不能只报 Live Coding 成功。
- 相关逻辑测试通过；数据校验无缺失引用或未确认字段进入开放名单。
- PIE 用于快速验证，但还须运行 Windows 打包版；检查默认地图、UI资源、输入、音效和特效被正确烘焙。
- 至少两个独立游戏进程完成加入、购买、施法、死亡、观战、下一回合和整场结算。
- 同一打包版进程使用两只真实手柄，验证分屏、独立瞄准与商店、死亡观战、断开重连及下一回合；完成双人FFA加AI和双人同队对AI。机器人遵守同样的数值、冷却和经济。
- BUG/CHECK 清单中本次范围所依赖条目已关闭或明确禁用相应功能。
- 输出可运行包、启动步骤、实际验证记录和剩余限制；没有实际运行的环节明确标注，不补写成功结果。

## 变更和回归

每轮开发先检查已有修改，避免覆盖用户工作。保持小范围实现，完成后记录行为、验证和待试玩项。修复影响结算顺序、价格、物品恢复或来源归属时，重跑对应数值与网络案例；不为低影响文字修改重复整个测试矩阵。

首版未完成的功能保持关闭。只有该阶段所有出口通过，才将里程碑标为完成。没有用户指示不自动提交、推送或发布发行包。
